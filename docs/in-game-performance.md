# 局内启动器开销优化

## 背景与范围

启动器与游戏核心运行在同一进程，还通过注入接入游戏。隐藏启动器画面并不会自动停止协程；共享的 CPU、磁盘、内存分配与 GC 仍可能影响游戏帧时间。

本次针对大模组反馈中找到的两类可避免开销实施修复：模组游玩统计的重复扫描/哈希，以及不可见启动器页面的轮询。代码审计能证明这些额外工作存在，但不能据此认定它们是所有掉帧反馈的唯一原因。

## 已实施

### Android 游戏核心 DEX 编译

Android 启动器会注入原版核心，再把修改后的 JAR 转为 DEX 动态加载。原来调用的 `javassist.android.DexFile.addJarFile()` 使用默认 `CfOptions`，其中 `optimize=false`；APK 为 Release 并不会改变这条运行时转换路径的编译参数。

现在由 `OptimizedGameDexCompiler` 显式设置 `CfOptions.optimize=true`，保留原 DX 后端、游戏逻辑和注入配置。写入时继续先打开描述符再把 DEX 标记只读，失败时清除不完整输出。APK 覆盖安装仍通过既有 `androidInstallationId` / `InstallArtifactMaintenance` 作废旧产物，首次启动重新生成优化后的核心，无需清除用户数据。

同一份未注入 Android 核心的静态 DEX 指令对比：基础单位更新 `bp.a(F)` 为 4,992 → 2,648 条，模组单位更新 `custom.j.a(F)` 为 3,674 → 1,556 条。此数字不能换算为 FPS 提升比例，也不表示 Android 运行时没有进一步的 JIT 优化。

2026-10-25，用户报告基于 1.20.29、仅改变核心 DEX 优化的 Release 对照包有效。包内原始核心 JAR 与注入配置和未优化对照包一致，签名及非调试标记均已校验。目前反馈为定性改善，尚未收到标准化帧时间曲线；也不能把这项 Android 专用修复视为桌面端掉帧原因。较早的 1.20.5 / 1.13.70 APK 同样关闭了此优化，尚不能据此定位最近版本回退的唯一提交。

优化增加首次编译的内存需求：桌面 JVM 的未注入核心转换在 256MiB 堆下通过、128MiB 下失败，这不是手机内存峰值测量。低内存设备的首次生成和扩展注入仍需真机覆盖，禁止静默退回未优化编译并当作优化成功。

回归：`OptimizedGameDexCompilerTest` 比较真实核心优化前后的全部类和方法集合、热点代码大小，并用当前生成的完整注入配置生成 JAR 后执行优化转换。

```powershell
.\gradlew.bat :rwpp-android:testDebugUnitTest :rwpp-android:compileReleaseKotlin --console=plain
```

### 模组统计和隐藏界面轮询

| 工作 | 原行为 | 修复后 |
| --- | --- | --- |
| 本局生效模组识别 | 登录后每秒复制、筛选单位定义表，枚举模组，读取名称和路径 | 每局首次有效采样创建快照；后续只读轻量状态和快照 |
| 本地模组内容身份 | 每个统计会话重新读文件；目录还需要生成规范化 ZIP 流 | 复用进程内和磁盘哈希缓存；同源并发请求串行计算后复用 |
| 房间界面采样 | 隐藏后仍可定时获取玩家、房间信息、名片和同步进度 | 只在可见等待房间采样；进游戏或隐藏窗口后挂起 |
| 好友、私信、账号页轮询 | 全局/页面协程可能随隐藏的 Compose 继续运行 | 隐藏后取消，返回后立即刷新；好友列表批次在请求之间检查取消 |
| 公示剩余时间 | 每秒递减，直接暂停会漏算局内经过的时间 | 使用单调时钟截止时间，恢复后重新查询服务器 |

### 模组统计

- `ModPlaytimeSnapshotCache` 在 Main 线程捕获本局模组及不可变名称/路径；新局、普通重载和保连接重载使快照失效。空模组集合也缓存，避免原版局重复扫描。
- 每秒轻量采样仍保留，用于正确识别暂停、切后台、观战、战败、回放和结束状态。统计资格与时长累计规则不变。
- `KeepConnectedReload`、`ModLoadSafety.loading`、`GameStartSafety.requiresRestart` 期间返回不可靠且停计的采样，不读取重建中的单位表。
- `ModPlaytimeHashCache` 保存到应用内部 `cache/mod-playtime-hashes-v1.json`，最多 256 项；只含规范化路径、文件元数据指纹和 SHA-256，不含账号或 Token。
- 单文件比较长度与修改时间；目录比较排序后的相对路径、类型、文件长度和修改时间。缓存命中仍需检查元数据，但不读取文件正文、不压缩目录。
- 哈希前后检查元数据与写入代次；计算中变更、取消、目录越界链接/循环不写入结果。缓存损坏、旧格式或写入失败不会阻断游戏。
- 应用导入、替换、删除模组前主动调用 `sourceChanged`，覆盖保留旧修改时间的替换。新增模组写入入口也必须接入此失效钩子。
- 已验证的网络模组仍优先使用 `NetworkModCache` 描述中的内容身份，保持房主名称和传输 SHA-256 口径。

限制：首次遇到新内容仍需完整哈希，目录元数据遍历也仍有成本。外部工具若修改正文却同时保持路径、长度、修改时间完全不变，元数据缓存无法检测；删除该缓存文件可强制重算。此缓存只供游玩统计，不能用作同步下载或安全校验的替代。

### 页面可见性

- `LauncherVisibility` 由真实平台生命周期维护：Android 的 MainActivity 暂停/恢复和游戏 Activity 创建；PC 的 Menu/Game 切换及窗口最小化/恢复。
- 协程内部直接收集 `StateFlow` 并通过 `collectLatest` 取消上一轮，不依赖 Android 后台停止后的 Compose 重组。
- `RoomSnapshotStore.shouldSample` 额外要求处于 Room 页面且尚未开局/启动。恢复可见可能早于平台清除局内标志，一次性房间效果会等待短暂交接。
- 隐藏期间不启动下一轮界面请求；已进入同步 HTTP 的单次请求可能等响应/超时后结束，但取消后不继续整个批次，也不提交迟到的界面状态。
- 房间名片回写还校验房间代次和账号会话，避免旧房间/旧账号响应污染当前状态。

保留账号在线心跳、房间身份公示 TTL、模组同步注册与续期、加入者下载/应用任务、退房清理、引擎网络保活以及必要统计上报。这些任务有会话职责，不能按页面可见性一起停止。暂停好友/私信轮询意味着对局中不再主动拉取新的私信和邀请，返回启动器后补刷。

## 自动验证

```powershell
.\gradlew.bat :rwpp-core-api:test `
  :rwpp-core:testDebugUnitTest --tests ModPlaytimeControllerTest --tests ChatMessageChangesTest --tests AccountPresenceHeartbeatTest `
  :rwpp-core:desktopTest --tests '*RoomPollingVisibilityTest' --tests '*SessionLifecycleTest' `
  :rwpp-desktop:compileKotlin :rwpp-android:compileDebugKotlin --console=plain
```

覆盖重点：

- 1,000 次同局读取只捕获一次，空集合、重载失效和捕获失败重试。
- 跨局/跨缓存实例复用内容身份；并发只计算一次；文件/目录增删改名、显式替换、取消和损坏缓存。
- 两局复用同一哈希，同时生成不同统计会话并保留各自时长。
- 虚拟时间推进隐藏的 60 秒不增加轮询次数，恢复立即执行；隐藏房间采样不调用引擎 getter。
- MockWebServer 验证隐藏时只完成已经发出的好友请求，恢复后完整刷新一轮。
- 账号在线心跳与原有会话退出/重入回归。

Windows 符号链接测试在系统不允许创建链接时提前返回，该环境下仍需在支持链接的平台补验。

## 真机验收（待完成）

自动测试和编译不能代替 FPS 对比，目前没有实际帧率改善百分比。Android 与 PC 分别按以下方式验证：

1. 固定设备、分辨率、图形设置、局内辅助开关、账号状态、同一大模组版本及存档/回放；保持相同镜头、游戏速度和单位数量。回放不计游玩时长，统计性能验收应使用实际对局/可继续游玩的存档。
2. 对比改动前后同一段 3–5 分钟对局，记录平均 FPS、帧时间分布/卡顿、CPU、分配/GC 与磁盘读取；每组重复，避开温控降频差异。
3. 分开观察首次冷缓存和第二局热缓存；重启应用后再进一局，确认磁盘缓存仍生效。
4. Android 验证遭遇战、任务、多人、回放、切后台和返回；PC 验证 Menu/Game 切换和最小化。返回等待室应立即补刷好友/房间状态，公示倒计时应与服务器校正。
5. 验证暂停、观战、战败不误计时；跨局报告不串局；修改/替换模组后不复用旧内容身份。多人保持连接、房主同步续期和退房清理应正常。
